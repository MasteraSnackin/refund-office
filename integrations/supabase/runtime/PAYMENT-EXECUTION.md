# Optional Stripe test execution preparation

Migration `004_payment_execution.sql` is optional and must not be applied to either running preview. It leaves every existing case and immutable `local-disabled` reservation unchanged. Separately gated hosted routes can use this prepared module; the local office routes cannot execute payments. Tests use injected Stripe responses, and no Stripe account, credential or endpoint has been used.

The prepared hosted reviewer screen uses the additive `006_payment_review.sql` for read-only context. Migration 006 requires 001, 002 and 004; it is also excluded from the ordinary preview. The screen records authorisation and reads saved results. Submission and reconciliation remain separate executor operations.

A separate reviewer decision is required before any execution. It binds the original approval ID and fingerprint, exact current case revision, unchanged original investigation facts, original reserved amount and explicit mapping `{accountId, paymentIntentId, orderId, paymentAmountMinor, currency:'gbp', livemode:false}`. The PaymentIntent must already exist; this module never creates payments or adds order metadata. The executor independently reads its account, PaymentIntent and charge before submitting a refund. The PaymentIntent must identify the exact order and tenant in its metadata.

The optional migration adds membership role `payment-executor`. Current local profiles remain reviewer and investigator; neither can claim, submit, reconcile or settle an execution. Administrative membership provisioning is separate. SQL derives every actor from `auth.uid()`.

Public RPCs, all with `p_tenant_id uuid` first:

- `refund_runtime_payment_authorisation_context(p_case_id text)` (migration 006): reviewer only; returns eligibility, the exact saved approval binding and any existing execution without changing state.
- `refund_runtime_authorise_execution(p_operation_id text, p_expected_case_revision bigint, p_original_approval_id uuid, p_original_fingerprint text, p_expected_amount_minor bigint, p_mapping jsonb, p_note text, p_command_id uuid)` — reviewer only; returns execution JSON.
- `refund_runtime_read_execution(p_execution_id uuid)` — reviewer or payment-executor; returns execution JSON.
- `refund_runtime_claim_execution(p_execution_id uuid, p_lease_seconds integer default 30)` — payment-executor only; claims an unsubmitted authorisation with an actor-bound lease and increasing fence.
- `refund_runtime_begin_submission(p_execution_id uuid, p_fence bigint, p_payload_digest text)` — payment-executor only; rechecks facts and persists the submission intent before any provider POST.
- `refund_runtime_save_refund_reference(p_execution_id uuid, p_fence bigint, p_refund jsonb)` — payment-executor only; records a matching provider response identity, without claiming independent verification.
- `refund_runtime_note_execution_unknown(p_execution_id uuid, p_fence bigint, p_error_code text)` — payment-executor only; keeps uncertainty and any known refund ID.
- `refund_runtime_claim_reconciliation(p_execution_id uuid, p_lease_seconds integer default 30)` — payment-executor only; requires a saved refund ID and never permits another POST.
- `refund_runtime_record_refund_readback(p_execution_id uuid, p_fence bigint, p_refund jsonb)` — payment-executor only; records a matching independent provider retrieval.

The execution DTO retains `id`, `tenantId`, `operationId`, `caseId`, `originalApproval`, `originalOperation`, `authorisation`, `mapping`, `payload`, `payloadDigest`, `idempotencyKey`, `status`, `fence`, `leaseActor`, `leaseUntil`, `submittedAt`, `refundId`, `receipt`, and `lastError`. Authorisation, mapping, original facts, payload and retry key are immutable. There is at most one execution per original reservation.

## Reviewer context and saved commands

`GET /api/cases/:id/payment-authorisation` calls the context RPC through the verified reviewer's own session. The hosted and optional payment gates run before this read. The response contains `tenantId`, `caseId`, `caseRevision`, `eligible`, `blockedReason`, `binding` and `execution`. When present, `binding` contains the original operation and approval IDs, fingerprint, exact case revision, refund amount, order/line IDs, original order total, currency and approval actor/time. The server derives these values from saved records. The lookup makes no Stripe request.

An eligible context has an unchanged, unsubmitted original reservation and no saved execution. An existing execution returns the full saved record and blocks a new authorisation, even if the current case has subsequently changed. This allows a reload or lost authorisation reply to recover the existing identity. The lookup does not claim that a payment was submitted or that a provider response is authentic.

The browser asks for the existing test account ID, PaymentIntent ID, a new reason and explicit confirmation. It takes the approval binding and amounts from the context, then saves the complete authorisation payload and stable UUID before POST. Storage is scoped to the workspace, user, role and case. If that write is unconfirmed, the screen retains the original command and permits only an exact retry or a read of saved state. It cannot replace the mapping, amount or reason while the original result is unknown. The command remains available after a confirmed response; a saved execution must match the original decision before the screen accepts it.

The result screen distinguishes `authorised`/`claimed` from submission intent and uncertain outcomes. `response-saved` and `reconciling` await independent retrieval; `pending` is not completion. `succeeded` and `failed` show the executor's saved matching receipt. A reviewer can refresh that saved record but cannot invoke submission or reconciliation. Receipt authenticity still depends on the trusted executor and actual provider acceptance.

## Executor and provider boundary

Submission intent is irreversible in this stage. A lost response without a saved refund ID is held as uncertain. It cannot be reclaimed, posted again, assigned a new retry key, or reconciled by guessing a refund ID. A known refund can be retrieved under a new reconciliation fence. Successful settlement is a trusted executor's attestation of a matching independent readback; SQL cannot itself verify an external provider. The prepared JavaScript executor enforces the readback sequence. Live Stripe behaviour remains unverified.

The JavaScript gate requires `REFUND_OFFICE_NETWORK=enabled`, `REFUND_OFFICE_PAYMENT_EXECUTION=stripe-test`, and `stripe-runtime` in `REFUND_OFFICE_ENABLED_INTEGRATIONS` before repository/provider work or credential reads. The default is disconnected. Only `sk_test_` or `rk_test_` credentials are accepted, and the actual provider adapter has no local payment fallback. Connected-account routing is outside this stage; the test key's own account must equal the authorised mapping.

`server/runtime-payments.mjs` exports `createRuntimePaymentRepository({env, tenantId, rpc})`, `createRuntimePaymentExecutor({env, repository, provider})` and `createRuntimeStripeTestProvider({env, fetchImpl})`. The repository transport receives an allowlisted full RPC name and named parameters. It must use the verified actor's own authenticated session. The executor offers `execute(executionId)` and `reconcile(executionId)`; it never authorises a decision. The separately authenticated reviewer calls `authoriseExecution` with the exact saved original facts and a stable command UUID. Reusing that UUID with changed input is rejected.

The executor verifies the account, existing succeeded test PaymentIntent and captured test charge before saving submission intent. It checks their exact amount, currency and order/tenant metadata, and the charge's remaining balance. After the single refund POST, it saves the matching refund identity, independently reads that saved identity, retrieves the refund from the provider, then saves and independently reads the result. A lost acknowledgement at any point after intent is an uncertain result. A provider response on its own never counts as independently confirmed.

Run the injected unit checks with `node --test tests/runtime-payments.test.mjs tests/hosted-payments.test.mjs tests/payment-authorisation-ui.test.mjs`. The explicit `node scripts/test-payment-review.mjs` harness exercises migrations 001–006 in a newly created disposable PostgreSQL container with no network, published ports, existing data mounts or provider access. It records evidence under `work/payment-review/database/`. The earlier `node scripts/test-runtime-payments.mjs` harness and `work/runtime-payments/` evidence retain their execution-only scope. Ordinary tests and local previews do not apply these optional payment migrations. The separate clarification rehearsal adds 007 to 001/002; it grants no payment execution authority.
